# 세션 실행 계획 — 순서와 인계

> 페르소나 정의는 `.claude/agents/qa-*.md`, 공통 규칙은 `docs/qa/browser-qa-guide.md`.

## 왜 순서가 정해져 있나

세션들은 독립적이지 않다. **앞 세션이 뒤 세션의 데이터를 만든다.**
원장이 매장을 열지 않으면 선생님이 들어갈 곳이 없고, 선생님이 알림장을 발행하지 않으면
보호자가 볼 것이 없으며, 발행이 없으면 공개 링크 토큰도 없다.

## 동시에 몇 명까지 되나 — 쿠키 저장소가 상한이다

**탭을 여러 개 여는 것과 페르소나를 여러 명 두는 것은 다르다.**

이 앱의 세션은 `pawlog-dev_access_token` 쿠키 하나이고, 도메인이
`.pawlog-dev.doyeonism.com` 이라 **그 도메인의 모든 탭이 같은 쿠키를 공유한다.**
탭 2에서 다른 계정으로 로그인하면 탭 1도 그 순간 같은 사람이 된다.

우회는 막혀 있다. 쿠키가 `httpOnly` 라 JS 로 탭마다 다른 토큰을 심을 수 없고,
`(checkauth)` 레이아웃이 **SSR 에서** 쿠키를 읽어 인증을 판정하므로 클라이언트 쪽
트릭이 닿지 않는다. 서브도메인을 갈라도 소용없다 — `.` 으로 시작하는 쿠키 도메인이
모든 서브도메인을 덮는다.

여기에 에이전트 층의 제약이 하나 더 있다. 하나의 Claude 에서 서브에이전트를 여러 개
띄워도 **MCP 연결은 하나**라 전부 같은 Chrome 을 조작한다. 둘이 동시에 돌면 서로의
활성 탭을 뺏어가며 클릭해서, 격리 이전에 **결과 자체를 믿을 수 없게 된다.**

### 그래서 이렇게 한다

| 구성 | 동시 페르소나 | 상태 |
| ---- | ------------- | ---- |
| 한 프로필, 탭 여러 개 | **1명** | 격리 불가 — 탭끼리 쿠키를 공유한다 |
| 일반 창 + **시크릿 창** | **2명** | ✅ 확실히 된다. 저장소가 2개다 |
| **Chrome 프로필 N개** (또는 다른 브라우저) | **N명** | ✅ 격리는 된다. ⚠️ 하나의 Claude 가 여러 프로필을 조작할 수 있는지는 **미확인** |

**격리 자체는 프로필을 나누면 해결된다** — 프로필마다 쿠키 저장소가 완전히 별개다.
남은 문제는 격리가 아니라 **Claude in Chrome 확장 하나가 여러 브라우저/프로필에
닿는가**이고, 이건 확장을 연결한 뒤 확인해야 한다:

1. Chrome 프로필을 하나 더 만들고 거기에도 확장 설치 + 사이트 권한 부여
2. 두 프로필 창을 모두 열어 둔 채 브라우저 조작 도구를 호출
3. 도구에 **타겟/윈도우 지정 파라미터가 있는지**, 없으면 어느 창이 잡히는지 확인

되면 프로필 N개로 간다. 안 되면 위 표의 2행(일반+시크릿, 한 세션에서 2명)으로 내려가거나,
프로필마다 Claude 세션을 따로 띄운다.

시크릿 창은 **전체가 하나의** 별도 저장소를 공유한다 — 창을 3개 열어도 2명이 상한이다.
시크릿에서 확장을 쓰려면 확장 설정에서 "시크릿 모드에서 허용"을 켜야 한다.

### 격리가 풀려도 크게 병렬화되지는 않는다

세션 1~4 는 **데이터가 앞뒤로 물려 있다**(위 "왜 순서가 정해져 있나"). 네 명을 동시에
띄워도 뒤 세 명은 앞이 끝날 때까지 기다린다. 병렬이 실제로 값을 하는 곳은 두 군데다:

1. **세션 5·6 을 1~4 와 나란히** — 표적 데이터만 확보되면 독립적으로 돈다
2. **아래 "두 명이 동시에 필요한 검증"** — 순차로는 아예 검증되지 않는 항목들

**기본은 한 번에 한 명, 순서대로.** 세션을 바꿀 때는 반드시 로그아웃한다(가이드 §2).

### 두 명이 동시에 필요한 검증

아래는 병렬이 편해서가 아니라 **그 방법밖에 없다.** 한 명씩 순서대로 하면 "바꾼 뒤
다시 로그인했더니 반영돼 있더라"가 되는데, 그건 다른 명제다 — **이미 열려 있는 세션에
변경이 도달하는가**를 봐야 한다.

| 검증 | 일반 창 | 시크릿 창 |
| ---- | ------- | --------- |
| 매장 정지가 즉시 듣는가 (세션 5) | 정운영자 — 매장 정지 | 박원장 — `/tenant/qa-school` 열어 둔 채 조작 |
| 새 필수 약관이 기존 사용자를 다시 걸러내는가 (세션 5) | 정운영자 — 약관 활성화 | 이보호자 — 동의를 마친 상태로 `/app` |
| 초대가 상대 화면에 뜨는가 (세션 1→2) | 박원장 — 초대 발송 | 김선생 — 초대 목록 |
| SUPER_ADMIN 강등이 즉시 듣는가 (세션 5) | 정운영자 — 강등 | 대상 계정 — `/admin` 열어 둔 채 |
| 탭 A(매장) · 탭 B(개인) 스코프 간섭 (세션 6) | 같은 사람이므로 **한 창에서 탭 2개**로 한다 | — |

이 항목들은 "정지시켰다 → 상대 창을 **새로고침** → 막히는가"까지 확인한다.
새로고침 없이도 막혀야 한다고 기대하지는 않는다(레이아웃 가드는 요청 단위다).

## 세션 0 — 준비 (사람이 한다)

1. **Claude in Chrome 확장을 연결**한다. 확인 방법: 세션에서 `mcp__claude-in-chrome__*`
   도구가 잡히는지. 안 잡히면 페르소나 에이전트는 브라우저를 조작할 수 없다.
2. `https://pawlog-dev.doyeonism.com` 에 **사이트 권한을 부여**한다 (확장 설정).
3. 페르소나 계정 4개를 발급한다 (가이드 §3 스크립트).
4. dev 스택이 살아 있는지 확인:
   `curl https://pawlog-dev.doyeonism.com/api/pawlog-dev/v1/health`
5. **카카오 로그인을 사람이 한 번 직접 통과**해 본다. 에이전트가 못 하는 유일한 인증 경로이고,
   `apps/web` 의 **실제 유일한 로그인 방법**이다. 여기가 깨져 있으면 나머지 테스트가 전부
   무의미하므로 제일 먼저 확인한다.

## 세션 간 인계 — 반드시 기록해서 넘길 것

각 세션은 끝날 때 아래를 **다음 세션이 쓸 수 있는 형태로** 남긴다.
없으면 다음 세션이 처음부터 다시 만들어야 하고, 그러면 데이터가 갈라져 결과를 못 믿는다.

**세션 1 → 2·3·6**
- 매장 서브도메인 (`qa-school`), 매장 ID
- 원생 이름과 **ID** (`QA초코`, `QA두부`)
- 요금제 이름과 판매한 이용권 **잔여 횟수** ← 세션 3이 이 숫자와 대조한다
- 프로필 사진의 **파일 ID** ← 세션 6이 접근을 시도한다

**세션 2 → 3·4**
- 발행한 알림장 ID
- 발행한 피드 게시물 ID와 **각 사진에 태그된 아이** ← 세션 3의 팬아웃 검증 기준
- 등원 체크로 **차감된 횟수** ← 세션 3의 잔액 검증 기준

**세션 2/1 → 4**
- 공개 링크 `/r/<token>` 전문. 알림 발송 이력 화면에서 얻는다

**세션 1 → 6**
- 표적 매장의 원생/알림장/파일 **ID 목록**

## 세션 6 이후

각 세션의 리포트를 모아 심각도순으로 정리한다. 그때 반드시 갈라서 볼 것:

- **critical/major** → 즉시 처리 목록
- **minor** → 디자인 시스템 위반인지(`docs/design-system.md` 대조) 개별 버그인지 구분
- **question** → 사람이 판단. 여기에 "의도한 것인데 사람이 버그로 읽었다"가 섞여 있으면
  그건 코드 버그가 아니라 **화면이 설명을 안 한 것**이므로 UX 항목으로 옮긴다
